### 2.3 ⭐ `<@openid>` 字段：是身份 ID，是降级渲染

```
<@0123456789ABCDEF0123456789ABCDEF>      ← 公开镜像里已替换为占位符（真值属第三方个人信息）
  · QQ 开放平台的 @ 提及标记，32 位十六进制 = 该用户【在此 bot 下】的唯一 ID
  · 不是 QQ 号（uin）—— 开放平台按 bot 隔离
```

**同一 QQ 会话内的两种 @（实测，`session-1ce37c8b`）：**
```
turn 25  prompt ：「群里第二条鱼妄图跟你那两个…」
         response：「@没关西，我不摸鱼谁摸鱼 …」        ← ⭐ 有昵称，可读

turn 27  prompt ：「有没有什么表情包适合<@F164B8829…> 这位仁…」
         response：「这位我这边只有一串 ID——看不见脾气，也看不见梗。
                     让我挑一张「适合他」的，那不叫推荐，叫瞎猜」  ← ⭐ 只有 ID
```

**⇒ 拿得到昵称 ⇒ `@昵称`；拿不到（另一个机器人 / 未授权实体）⇒ 露出 `<@openid>`。这是【降级渲染】。**
**⭐⭐ 结论：这个字段对每个用户都不同 —— 它正是"谁在说话"的身份锚点，可用作记忆分桶的键。**

```
   chatId, threadId, botId, sentAt]

```

## 3. ⭐⭐ 设定者的裁定：情绪不分对象

> 「按一种情绪设立，就先不搞对象分化了」

```
✅ 引擎只有【一条 E】—— 大肥鱼此刻的情绪
✅ 不做「对 A 的情绪」/「对 B 的情绪」的多对象分裂

理由（本鱼赞同，记下以便日后回看）：
  大肥鱼是【一条鱼】，它此刻只有一份情绪。
  人的区别应该体现在【对谁的多巴胺高】（attachment 对象偏移），
  而不是把情绪劈成 N 份 —— 后者会损害人格一致性。
```

**⚠️ 但由此明确一个边界：**
```
记忆【按人分桶】（因为要"记住每个人说了什么"）
情绪【全局一条】（设定者裁定）
⇒ ⭐ 两者的作用域【不同】，这是刻意的，不是疏漏
```

## 4. ⭐⭐⭐ 情绪衰减公式 v1（本次推导，本方案的核心）

### 4.1 两个来源

```
情绪衰减理论（本项目 A2）:
   E_t = μ + ρ(E_{t−1} − μ) + g·h(n)·ΔE
   ⇒ 等价于  E_t − μ = Σ_i ΔE_i · ρ^(t − t_i)          ρ 全局常量

记忆衰减理论（SuperMemo / Wozniak 1995）:
   R = exp(−t / S)                                     S 逐事件
```

### 4.2 糅合

```
⭐ 因为  ρ^Δt = exp(−Δt · λ)  ，λ = −ln(ρ)
   ⇒ 两式【同族】，差别只在 ρ 是"全局"还是"逐事件"

【情绪衰减公式 v1】
   E_t − μ = Σ_i ΔE_i · exp( −(t − t_i) / S_i )

     ΔE_i        = 第 i 个事件的冲击        （评价层产出）
     S_i         = 第 i 个事件的稳定性      = S0 · (1 + k · intensity_i)
     intensity_i = 该事件的情绪强度         （评价层产出 —— S 挂评价层）
```

### 4.3 ⭐ 与原 A2 的关系：A2 是 v1 的特例（已数值验证）

```
取 S0 = 1/λ = 13.192 轮（使 intensity=0 时 S=S0 等价于 ρ=0.927）、k = 0：
   v1(T=12) = 0.6012345318
   A2(T=12) = 0.6012345318
   差 = 1.110e-16   ✅ 精确退化
（脚本：demo/derive-emotion-decay.js）
```

### 4.4 行为差异

```
两个事件、ΔE 相同，强度不同（S0=42.27, k=4）：
   A @轮1 intensity=0.1  ⇒ S = 59.18
   B @轮1 intensity=1.0  ⇒ S = 211.35

   Δ轮=20   A 残余 0.7132 ｜ B 残余 0.9097 ｜ 比 1.28
   Δ轮=60   A 残余 0.3628 ｜ B 残余 0.7528 ｜ 比 2.08
   Δ轮=150  A 残余 0.0793 ｜ B 残余 0.4918 ｜ 比 6.20
⇒ ⭐ 同样大的冲击，强情绪的那份留得久得多 —— 单一 ρ 做不到
```

### 4.5 ⚠️ 一个重要的实现后果

```
⚠️ 变成 v1 之后，【递推写法不再适用】——
   因为每个事件的衰减率不同，不能只用"上一轮的 E"推下一轮，
   必须保留【事件账本】。

⇒ ⭐⭐ 所以「情绪记忆账本」从【附加模块】变成【引擎的必需组件】！
   一份账本，两用：
     · 算出当下的 E（v1 的求和）
     · 注入给 LLM（按情绪残余排序）
```

## 5. ⭐ 接入架构（数据流）

```
QQ 群消息
   │  （平台级 @ 触发 ⇒ 只处理被 @ 的消息）
   ↓
dsh-im 插件
   │  · 取 senderId（openid）/ senderName —— ⚠️ 必须【运行时】取，事后补不了
   │  · 注入 contextEnhancement.fields
   ↓
Emotion Engine
   │  ① 评价层 → ΔE / intensity / 情绪词
   │  ② 写入【情绪账本】：{ turn, at, senderId, summary, emotion, intensity }
   │  ③ 按 v1 求和 → E
   ↓
情绪记忆检索
   │  · 关键词/摘要触发 + 按情绪残余 R 排序
   │  · ⭐ 按 senderId 过滤（"这个人"的那几笔）
   ↓
注入 LLM（自然语言，相对时间词）
   ↓
回复 QQ 群（@ 回对方）
```

## 7. 风险与后续改进

```
① senderId 事后不可重建 —— 若运行时忘了取，这段记忆就永远是"无名氏"
② 群友互相污染 —— 若检索忘了按 senderId 过滤
③ v1 改递推为求和 ⇒ 每轮计算量从 O(1) 变 O(事件数)，长会话要留意
④ 「本会话保留」在 QQ 群里语义变了（一条会话里有 N 个人）
⑤ 多对象情绪（对 A / 对 B 分开）—— ⭐ 本次【刻意不做】，列为后续改进
⑥ 跨会话持久化 —— 本次不做
```
